# P3 — builder notes, disagreements and proposals (2026-09-28)

Written per the wave task instructions: disagreements are not silently deviated from — the spec was
followed in every case below; this file records where I think the contract itself should change, and
what was measured.

## 1. `in-the-black` ($1.5M by day 365) — followed, calibrated to $800k, and it is a thin mission

**Spec followed:** goal type `cash`, winnable-by-script + not-won-by-idle hold (the calibration rule
explicitly permits changing placeholder numbers).

**Measurement (seed 1, fresh loads, 365 days):** the idle demo park ends at **$791,777** net. Every
"positive" script I tried earns *less* than idle:

| script | 365-day net | why it loses |
|---|---|---|
| idle (the demo park as built: $15, pre-staffed) | $791,777 | — |
| buy lion+rhino+elephant + hire | $433,663 | attraction is already clamped at 1.0 (11 species all at/over their `herd×0.5` sighting threshold) — bought animals are pure feed/vet cost |
| ticket $14 / $13 | $330,804 / $189,357 | arrivals push past park capacity (~225) → crowding tanks satisfaction → reputation compounds down |
| ticket $16 | $271,876 | price elasticity, plainly |
| fire 1 guide | $708,961* | arrivals grow past 6-guide coverage within ~100 days |
| place hides/shop/restaurant mid-game | $253,469* | building `flatten` re-floods zones and destabilises the built park (documented park fragility) |
| fire 1 ranger (need is 1, demo has 2) | ≈ $839,227 | the ONLY lever found: coverage stays 1.0, pure $130/day wage saving |

\* measured before I found the same-page contamination (see §3); magnitude indicative, ordering confirmed.

**Shipped number:** $800,000 — idle tops out $8,223 short; the ranger-trim replay crosses on ~day 341.

**Proposal:** the cash mission presumes a park whose economy has headroom a manager can unlock. The
demo park opens pre-tuned, so headroom is ~5%. Options for a later wave: (a) open the park
deliberately mis-managed when a mission is active (wrong price, over/under-staffed) so "playing
well" has room to matter; (b) wire P4's occupancy/tier-pricing into the income side first, then
re-raise the target; (c) accept it as a "don't destabilise a working park" mission and say so in the
brief. I did (c) with an honest brief; (a) is the one I'd pick.

## 2. `balanced-range` (demo value + 10) — followed, calibrated to 92 (demo + 3.55)

Demo day-1 index is **88.45** and the formula is already near its ceiling: richness 11/12, evenness
0.859, 4/4 big-five, 6/10 plants. "+10" (98.45) is unreachable — the maximum any script adds is
+3.33 (12th species) + ~1 per planted plant species (+1 each for sour_plum/knobthorn/marula, the
three below the 0.02 mean line; baobab too expensive per point). Idle drifts 87.7–89.6 over 240 days.
**Shipped floor: 92** — the replay (cheetah + three plantings ≈ 94–95) holds it; idle never touches
it. No contract change proposed; recorded because the spec's "+10" presumed a lower demo baseline.

## 3. The spec's one-page-via-`reset()` fallback for `mission-replay` is unsafe in the live game

The spec allows running the four-mission variants on one page through `simulation.reset()` "only
after a test proves reset → re-run is byte-identical". The test exists and passes (test.mjs,
headless: run → reset → re-run byte-identical, mission state included) — but in the **live** game
`reset()` is not a whole-game restart: `world.animals` belongs to the animals module (the ledger
restore cannot un-spawn the previous variant's births), and a `park.loadDemo()` rebuild flattens
terrain so the second build places differently (and re-charges the demo planting). Measured drift
across same-page variants: $791,777 → $722,696 → …. So the harness runs **every variant from a fresh
page load**, which is the spec's primary wording ("replayed from a fresh load"). If the verifier
wants cheaper runs, the fix belongs in a future wave: a core-owned full-game snapshot (world.animals
+ terrain + buildings) that `reset()` can restore — that is an integrator change, not something a
wave branch should improvise.

## 4. Minor: `mission:started` event not added

The spec lists exactly two events (`mission:progress`, `mission:completed`); I shipped exactly those.
A `mission:started` would let the ui open the objectives panel automatically when `?mission=` boots,
but the park's start toast covers the feedback today. Not proposed as a change — recorded so the
omission is visibly deliberate.
